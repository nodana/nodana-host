# Publishing host approvals and pinned host releases

Host approval data, publication and public release assets belong to
`nodana/nodana-host`. Phoenixd bundle releases remain in
`nodana/nodana-phoenixd`. The CLI downloads:

`https://github.com/nodana/nodana-host/releases/download/host-policy-v1/nodana-host-policy.json`

The host repository owns `policy/host-images.json` and
`.github/workflows/sign-host-policy.yml`. The workflow runs only on demand.
It calculates and displays the input checksum before approval, then signs and
publishes the policy plus per-image manifests and checksum files. There is no
expiry or scheduled renewal, and no EC2 image rebuild is required.

The workflow builds the `nd-host-policy` operator tool from a reviewed,
pinned `nodana-cli` commit. It does not compile the controller or build an AMI.
Host approval source data is checked out separately as data; it is not executed.
The CLI keeps a fixed policy fixture for tests, not the live approvals.

## Move publication to nodana-host

1. Review and commit/push the updated CLI, host repository workflow/data/docs,
   and removal of the old Phoenixd publication workflow. Do not release
   `v0.1.2` yet.
2. In **nodana-host → Settings → Environments**, use one environment:
   **host-policy-approval**, with **Required reviewers** and the secret
   **HOST_POLICY_SIGNING_PRIVATE_KEY_PEM**. That same environment protects both
   approval and signing; no second release environment is needed.

   The private key must match `nodana-cli/policy/signing-public-key.pem`.
   For this migration the CLI retains its existing trusted public key; configure
   the corresponding private key from your original secure key store.
   GitHub does not reveal an existing secret's value, so it cannot be copied
   out of the Phoenixd environment through the UI. No private key is committed.
   The host-specific secret and environment replace the bundle secret reference
   in the host publication workflow.
3. In **nodana-host → Settings → Secrets and variables → Actions → Variables**,
   set **HOST_POLICY_TOOL_COMMIT** to the exact reviewed, pushed CLI commit.
4. In **nodana-host → Actions → Publish reviewed host approval policy → Run
   workflow**, supply **host_source_commit**: the exact pushed host repository
   commit containing the reviewed `policy/host-images.json`. This is the
   approval-data commit, not necessarily the source commit of the running image.
   The manifest separately records the original image build's source commits.
5. Review the preparation summary and policy file, then approve the waiting
   **host-policy-approval** job. Publication signs using the host repository's
   environment, uploads all assets to its public `host-policy-v1` release,
   and verifies the exact public policy download.
6. Test the local 0.1.2 CLI against production using the commands below, then
   release `v0.1.2` from the CLI repository. Do not replace the existing 0.1.1 tag.

The old already-published Phoenixd `host-policy-v1` assets are left in place for
installed 0.1.1 clients, whose binary still requests that URL. The removed
Phoenixd workflow no longer publishes host approvals. New 0.1.2 clients request
only the host repository; there is no fallback to the old repository.
Publish and verify the host repository policy before releasing 0.1.2.

For command-line publication after one-time setup, run from the host checkout:

```sh
host_commit=$(git rev-parse HEAD)
gh workflow run sign-host-policy.yml --repo nodana/nodana-host \
  -f host_source_commit="$host_commit"
```

## Host release manifest format

Each manifest is canonical JSON with sorted keys and no whitespace:
`{"version":1,"image":<approved image entry>}`. It contains that image's PCR4,
PCR7, PCR12 and provenance. Its checksum is SHA-256 of these exact UTF-8 bytes;
the JSON file has no trailing newline. The checksum file contains the lowercase
hexadecimal value followed by a newline.

The same format is generated by the AWS `ndn-infra image-policy` command with
`--host-release-output DIRECTORY`, after the existing hardware/artifact
verification. That writes `host-release.json` and `host-release-sha256.txt`.
The public workflow uses AMI-qualified filenames so it can publish several
host releases together.

A host checksum is independent of approval-list ordering, serial and other
images. Changing that entry's measurements or provenance changes its checksum.
The CLI computes it from each signed image entry and verifies AWS measurements
against only the matching entry when a host pin is supplied. The manifest URL
is not a new trust source: the user's approved checksum is the pin.

For the currently verified production entry the checksum is
`f1c11830ff2ed73fa3d3f068b21e4dc5d9e4503b5b282d93674205b6c78048df`.

Test all three modes on the existing production node after publishing:

```sh
nd attest --url https://lark-3xii.nodana.app --approve-host-sha256 f1c11830ff2ed73fa3d3f068b21e4dc5d9e4503b5b282d93674205b6c78048df

nd attest --url https://lark-3xii.nodana.app --approve-release-sha256 a4a0855395db9b0996b8fa8eb7ad95ebbd40a21f675281ac73c5038162b21e29

nd attest --url https://lark-3xii.nodana.app --approve-host-sha256 f1c11830ff2ed73fa3d3f068b21e4dc5d9e4503b5b282d93674205b6c78048df --approve-release-sha256 a4a0855395db9b0996b8fa8eb7ad95ebbd40a21f675281ac73c5038162b21e29 --json
```

Host-only results explicitly mark the bundle as unpinned. Bundle-only results
use Nodana's signed host policy. Both modes still authenticate the full
host/node/bundle/certificate binding. No approval and a mismatching supplied
checksum fail; pinning one release never silently approves the other.

## Changing approvals

Use the existing hardware verification and `ndn-infra image-policy` process.
Compare boot measurements with the exact candidate build and Secure Boot
enrollment; never approve measurements solely from a node's live response.

In `nodana-host`, update `policy/host-images.json`, increment `serial`, and commit/push the
reviewed data. Run the same publication workflow with that host repository commit; its preparation
job calculates and displays the checksum for review before approval.
The trusted signing tool stays at `HOST_POLICY_TOOL_COMMIT`; change that variable
only when reviewing and updating the tool itself.

Remove obsolete image entries when replacing approvals. A signed empty image
list withdraws every approval. The workflow replaces the published policy;
users fetch it on their next attestation without a CLI update. There are no
background jobs or periodic maintenance runs.

Only independently verified production `ami-03f3b551d17c25f49` is included
initially. Staging needs its own verification before inclusion. A local
`NODANA_HOST_POLICY_FILE` still requires a trusted signature. Download failures
stop attestation rather than falling back to an old local policy.

An old saved policy retains a valid signature. Without expiry or a persistent
client rollback counter, its signature alone cannot establish that it is the
latest policy. Normal clients use the currently published policy over HTTPS.
The serial is an audit identifier; signing-key rotation requires a CLI release.

## Production verification on 26 October 2026

AWS identified Lark as `i-05a7915cca36df129`, running
`ami-03f3b551d17c25f49` from the `protected-host-production-v0.1.0` import record.
Its AMI UEFI enrollment matched the release's `uefi_data.aws` byte for byte;
runtime PK, KEK and db matched the enrollment.

PCR4 matched `tpm_pcr.json`. PCR7 was independently reconstructed from
SecureBoot=1, enrolled PK/KEK/db, empty dbx, the separator and the 48-byte db
authority entry, and matched the attested PCR7. PCR12 was zero. Build manifest,
provenance and predicted-PCR file checksums matched `SHA256SUMS`; provenance and
enrollment digests matched their manifest records.

Installed `nd` 0.1.0 then verified a fresh production proof using the independently
checked temporary policy: AWS signature/chain, freshness, nonce, TLS binding,
node identity and the independently obtained bundle checksum all passed. The
original failure was the CLI's stale compiled-in approval. No host or live policy
was changed during investigation. The new signed publication path must pass
step 5 above after initial publication before 0.1.2 is released.
